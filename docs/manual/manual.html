codewiki 使用手册

把三端代码与旧文档 compound 成可被验证的 LLM Wiki

codewiki 由 TypeScript CLI kb（Node ≥ 20）和一个 codewiki Agent Skill 组成，Claude Code、Codex、Gemini CLI 等 agent 都能直接使用。它把移动端 monorepo（Android Kotlin/Java、iOS Swift、HarmonyOS ArkTS，另支持 JS/TS）和遗留文档整理成适合 agent 使用的知识库。每次 merge 到 master 都会做一次增量更新。每个页面都通过“符号 ID + 内容 hash”锚定到代码，CI 中的 kb verify 负责证明这些知识与当前代码一致。

1项目目标

移动团队的“知识”通常散落在三端代码、过时的 wiki 和口口相传里。每次让 LLM 从零读仓库，成本高，结果也不稳定。LLM 一次性生成的文档则会漂移：代码改了，文档没改，也没人知道哪一页已经过时。codewiki 想解决三个问题：

  1. 知识复利：沿用 Karpathy 的 LLM Wiki 模式（raw sources / wiki pages / schema）。每次合并只重写受影响的页面，知识持续累积，不必每次从头生成。
  2. 可证明一致：页面 frontmatter 的 sources 记录“符号 ID + 归一化内容 hash”。CI 中 kb verify 检查所有锚点与 HEAD 是否一致，不一致就不发布。
  3. 三端对齐：用同一套 route_id、testID、API 描述 Android / iOS / 鸿蒙的同一个功能，并输出机器可读的 facts，供 e2e 测试（兄弟项目 e2epilot）、coding agent 和 CI 使用。
设计原则：确定性的事情交给 CLI（tree-sitter 抽取、diff、plan、verify），理解交给 LLM（写解释和语义核对），一致性靠硬校验（锚点 hash、写集、staging 验证后再原子发布）。

2.3 符号模型与增量判定

字段含义
id<platform>://<相对平台根路径>#<限定名>，例如 android://app/src/main/java/com/minishop/ui/cart/CartViewModel.kt#CartViewModel.addItem
hash去掉注释、归一化空白后 token 序列的 sha256。只改注释或格式视为 no-op。容器（class/struct）只计入自身头部和成员签名
sig_hash声明头（含注解、装饰器）的 hash，用来区分 body 变化和 signature 变化
refs函数体内引用的已知符号，按同文件 → 父类型被引用 → 全局唯一（结合调用点信息）的顺序解析
norm_hash / simhash去掉自身名字后的 body 指纹，用于识别 rename（完全一致记 1.0，同目录 simhash ≥ 0.8 记模糊 rename）

plan 规则：页面被判为受影响，要么是它自己的锚点发生了 body / signature 变化、被删除或改名，要么它锚定了“签名变化符号”k 跳以内的调用方（沿反向引用边传播，参考 RepoAgent）。facts 中出现新 route_id 时创建功能页。模块变化超过 50%，或结构变化（增、删、改名、签名变化）超过 30% 时，改为全量重建。

锚点精度：功能页只锚定路由所属的 screen、它的 ViewModel / store，以及 2 跳以内的接口。被 3 个及以上路由引用的符号归入 concepts/shared-components.md，路由器和深链处理代码归入 concepts/navigation.md。这样修改 BackButton 时只会重新检查共享组件页（有单测覆盖）。

3核心能力

所有命令都支持 --json、--root、--config、--wiki-dir、--quiet：数据写 stdout，日志写 stderr。退出码：0 成功，1 存在 stale 或 verify 失败，2 用法错误，3 内部错误。写文件的命令支持 --dry-run；全部非交互、可幂等重跑。

命令作用
kb init探测平台目录，生成 codewiki.yaml、wiki 骨架、AGENTS.md schema 和 .gitignore 条目
kb scantree-sitter 并行抽取符号和 facts（按内容 hash 缓存），报告 parse_failures
kb diff [--base sha]按符号 ID 比较新旧图，分为 unchanged / body / signature / added / deleted / renamed，并输出 changed_route_ids 和 changed_files
kb plan为每个受影响页面生成任务，带 reasons 和显式写集，写入 .kb/plan.json；超过阈值时改为全量
kb compoundscan → diff → plan → LLM → verify → 原子发布。支持 --llm template|claude、--fallback、--max-llm-tasks
kb verify / statusCI 门禁：锚点 hash、符号是否存在、死链、孤儿页、index 覆盖、facts / parity 是否最新；status 列出 stale 页面
kb discover-docs按 spec-kit、OpenSpec、Kiro、ADR、RFC、AGENTS.md、README、docs/ 的约定发现文档并分类
kb ingest把文档复制到 raw/docs，抽取断言（EARS、MUST/SHALL、FR-001、Kiro 编号），逐条判为 verified / conflict / unverifiable
kb search / get / context检索 wiki；按 id 取页面；查询某个文件对应的页面、符号、路由、testID、接口，以及锚定在该文件中的文档需求（供测试生成使用）
kb conflicts哪些文档过时：与代码矛盾的断言，附 文件:行号、代码证据和修改建议（MCP：kb_conflicts）
kb routes / lint-tid / parity按模块汇总路由并列出 dangling buildFunction；testID 覆盖矩阵（--pages：哪些页面设置了 testID；--top：最常用的 testID）；功能 × 平台一致性和跨平台常量差异
kb bench / eval冷 / 热扫描基准；用人工标注的 golden set 评测断言核对与 plan 影响面（precision / recall）
kb mcp / anchor / install / agentsstdio MCP server（7 个工具）；打印符号当前 hash；按 agent 安装 skill、指引块和 MCP 注册，可重复执行（install-skills 为别名）；列出 agent 支持矩阵

4使用方法

4.1 安装与初始化

npm i -g codewiki   # 或 npx -y codewiki …
# 从源码：npm ci && npm run build && npm link
cd your-monorepo
kb init           # 配置 + wiki 骨架
kb discover-docs --json > docs.json
kb ingest --manifest docs.json
kb compound       # 首次全量；--llm claude
kb verify         # CI 门禁

4.2 配置 codewiki.yaml

version: 1
wiki_dir: wiki
platforms:
  - {name: android, root: android}
  - {name: ios,     root: ios}
  - {name: harmony, root: harmony}
llm:
  cmd: claude -p --permission-mode ...
plan:
  hops: 1
  rebuild_module_ratio: 0.5

配置不需要手写：kb init 会自动探测平台目录，只有探测不准时才需要改。零配置：没有 yaml 时，kb routes / lint-tid / parity / scan / anchor 仍可直接运行，且不写入任何文件。wiki 类命令遇到未初始化的仓库，会提示先运行 kb init 和 kb compound --llm template，这一步是确定性的，不调用 LLM，只需几秒。skill 和 CLAUDE.md/AGENTS.md 指引块也写了同样的步骤。实测在未初始化的仓库里，Claude 会自行完成初始化，轮数从 12 降到 5。指定 --config <file> --root <repo> 时，wiki 会写到被分析仓库之外，用于只读分析第三方仓库。

4.4 CI、Skills、MCP 与 e2epilot

接入点做法
CI.github/workflows/compound.yml：push 到 master/main 时触发，concurrency 串行且不取消；actions/cache 缓存 kb 和 wiki/.kb/cache；有 ANTHROPIC_API_KEY 时用 --agent claude，否则有 OPENAI_API_KEY 时用 --agent codex，都没有时用 template。--max-llm-tasks 按价值排序分配预算（feature > flow > concept，同类再按变化锚点数排序）。verify 失败则 job 失败；成功时以 [skip ci] 提交 wiki
Skillskb install --agent … 安装单个 codewiki skill（SKILL.md 按任务路由到 references/ 下的 compound / ingest / query / lint / tree / ownership 说明）：Claude 装到 .claude/skills，Codex 和 Gemini 装到 .agents/skills。skill 只负责调用 CLI，不重新实现逻辑（实测见 6.4 和 4.5）
自建 gitkb hook install --mode post-receive --repo app.git。适用于 GitLab server hooks、Gerrit 和自建 git：push 到 master 后 compound，wiki 放在服务端，不回写 master（实测见 6.6）
MCPkb install --agent … --mcp 会写入 .mcp.json、.codex/config.toml、.gemini/settings.json、.cursor/mcp.json，命令为 kb mcp --root <repo>。提供 7 个只读工具：kb_search / get / context / anchor / status / parity / conflicts。Claude、Codex 和 Gemini 的真实 CLI 都已完成握手
e2epilotkb diff --json 和 plan.json 输出 changed_route_ids、changed_routes（附原因）和 changed_files（含 git 资源文件），供 e2e graph invalidate --changed-routes 和 e2e impact 使用

  • Codex 0.163.0 和 Gemini 0.65.0 的真实二进制通过本地 mock 模型 API 跑通了 kb compound：页面写入成功，越界文件被回滚，用量从各自的 JSON 事件中解析。

5多级目录（模块树）与文档所有权（SFK）

5.1 模块树：L0 仓库 → L1 项目 → L2 模块 → L3 功能簇

大仓库只有一层 features/* 时，agent 很难判断“这段代码属于哪个子系统”。kb compound 每次都会构建（首次运行或 --full）或增量修复 wiki/module_tree.json，并为每个节点生成一页：

层节点来源页面 / 索引正文中由 kb 维护的块
L0仓库pages/overview.md · index.mdkb:breadcrumb 面包屑、kb:children 子页表 + 摘要、kb:symbols 符号表、kb:routes 关联功能页、kb:diagram mermaid（带 hash）、kb:sources（Sources: path:起-止）。LLM 只写块外的叙述，块在写后由 kb 覆盖
L1Gradle settings、Package.swift、Xcode、hvigor；否则按平台目录pages/<p>/overview.md · pages/<p>/index.md
L2Gradle module、SwiftPM / Xcode target、HAP / HAR / HSPpages/<p>/<m>/overview.md · index.md
L3核心符号图 Leiden 聚类，模块超过 tree.budget_tokens 才拆pages/<holder>/<slug>.md
  • 稳定与增量：只有一个项目或模块时该层自动折叠。簇 id 通过 Jaccard 继承；增量修复按规则链放置新符号：rename → delete → same_file → same_dir → neighbor_majority → misc（标记 needs_review）。变化超过 tau_grow 时重聚类该模块，超过 tau_tree 时整树重建。
  • 自底向上写作：叶页读源码，父页只读子页摘要。子摘要变化会改变父页的 children_digest，父页随之 stale。frontmatter 新增 level / tree_node / parent / summary / importance / children_digest。
  • 校验：kb verify 额外检查树可解析且与页面一致（E_TREE_INVALID / E_TREE_PAGE_MISSING）、children_digest 是否最新（E_TREE_STALE）、kb 块和 mermaid hash 是否新鲜（E_KB_BLOCK_STALE）。每层的 index.md 和分层 llms.txt 由 kb 渲染。
  • 命令：kb tree build|show|explain|deps|patch（均支持 --json）。kb tree explain <symbol-id 或文件> 告诉 agent 这段代码属于哪一页、哪条路径；kb tree deps <模块> 给出构建依赖和被依赖（模块页上也有 kb:dependents 块），--top N 列出依赖最多和 fan-in 最高的模块；patch 先校验人工调整（rename 改名、merge 合并同级簇、split 拆簇），再写回树。

5.2 文档所有权（SFK）：kb docs

wiki/ 归 kb 所有；仓库 docs/ 和各项目的 <project>/docs/ 由人和 kb 共写。核心承诺是人写的内容一个字节都不改、不删、不重排：每次写入前 checkHumanContentPreserved 都会比对，违反则拒绝写入。

文件状态判定kb 的写法
new文件不存在只用已验证、带 **Source** 行的条目新建
managedfrontmatter 有 last_compound_scan按条目 key 替换或追加；人加的段落不动
skeleton只剩标题和 TODO / TBD / [DESCRIPTION] 占位去掉占位，按节插入
adopted有任何人写内容只在末尾追加 kb 段落
frozen.kb/docs-schema-extra.yaml 中 enabled: false，或未登记的自定义文档一字不动
  • 作用域与归属：一个 repository 加若干 project（apps/* 这类容器目录、android/ ios/ harmony/、scopes.projects）。有根证据、或 ≥ 2 个项目都有证据的条目写入仓库 docs，项目 docs 里只留一行 xref:；只有单个项目证据的写入该项目 docs；跨项目取值不同时，仓库条目标记 parity 差异。可用 --project、--no-root-write、--no-root-read 限定范围。
  • 条目来源：template 模式从 facts、模块树和 specs 确定性生成架构、导航、接口契约、testID、设计模式、功能目录、spec 索引和需求条目。--agent / --llm 模式下由 agent 按契约格式补写叙述，kb 校验 Source 行、归属和预算后才合并。中断后可用 --resume 或 --restart。
  • spec 信任：**Status**: 为 Implemented / Verified / Archived 时可信；Draft 只能产出 [Unconfirmed] 条目；kb 从不写 specs/。kb docs stale-specs 报告过期的 Draft、从未 Verified 的 Implemented，以及与代码冲突的 Implemented。
  • ADR 与技术债：kb docs adr 和 kb docs debt 默认只输出提案，加 --write 才新建 docs/adr/NNNN-*.md 或追加 docs/tech-debt.md 的 TD-NNN 行；已有 ADR 永不编辑。kb links 和 kb verify --docs 检查链接与 Source 路径。

5.4 真实仓库、真实 LLM 与架构类 A/B（详见 docs/validation-v2.md）

实验结果
8 个真实仓库上的 SFKnowinandroid、element-x-android、kotlinconf、HarmonyOS-Cases、sunflower、wikipedia-ios、NextE、DroidconKotlin，都在 git clone --shared 副本上运行。共检查 708 个人写 .md：改动 0、删除 0，独立检查和 kb guard 都是 0 违规。人写文档都是 frozen，kb 只在旁边新建文件；用 docs_schema 把维度指向 4 篇真实文档后，它们变成 adopted，kb 只做追加。kb 写的内容 0 坏链。修复了 8 个问题，包括 Gradle 子模块被当成项目、子目录里的 HarmonyOS 应用检测不到、index 路由与树索引冲突、--json 经管道输出在 64 KiB 处截断。
真实 LLM（haiku，demo/llm-demo.sh）写了 L3 簇页、L1 / L2 页（由子页摘要自底向上）和 53 条 docs 条目。docs agent 只有只读工具。每一步 verify 都 PASS，kb 块由 kb 覆盖，写集和人写内容的 guard 都没有触发。叙述具体（路由表、跳转关系、MAX_CART_ITEMS = 20）。共约 $0.15。
架构类 A/B（element-x，268 个模块，haiku）A 10/10、5.9 turns、$0.064；B 10/10、7.8 turns、$0.078。但 A 在依赖类题目上没有用 kb，差距视为噪声。加入 kb tree deps 后，8 次运行中有 7 次调用了它，答案与标准答案一致，但 turns 没有下降：agent 还会再 grep 一遍 build 文件核对。
热扫描（Cases，20141 个符号）三项改动：引用解析并行；按全部输入 hash 缓存解析结果；facts 结果缓存，并把 call sites 拆成单独文件按需加载。kb scan 整个进程从 2.2–2.9 s 降到 1.15–1.33 s（load 约 11.5），Go 版约 1.1 s。结果逐字节一致，有测试覆盖。
链接检查与 verify --docs反引号路径只在形如路径（以 ./ ../ 开头，或带已知扩展名、首段目录存在）时才检查，跳过代码片段、glob、占位符和兄弟仓库路径。NextE 的坏链从 506 降到 288，抽样精度 19/20。verify --docs 只在 kb 拥有的内容出错时失败；人写正文里的坏链列为 human_review_candidates，加 --strict 才算失败。
e2epilot 互通用新 clone 构建 e2e，对 TS 版 minishop facts 运行 seed / path / graph invalidate / impact --codewiki-diff / trace，全部 exit 0。新字段 name / deeplinks 向后兼容。

6.3 评测：kb eval（开发集 33 条 / 盲测集 31 条）

开发集（golden.yaml）有 33 条断言，并标注了每个变更集应该重检的页面；第 5 轮的规则就是看着它写的。盲测集（heldout/）由另一个 agent 编写，它没有读过规则代码，写了一份新的旧文档，共 31 条断言。

开发集上 template 第 5 轮准确率 0.97；盲测集上 template 0.58（conflict recall 0.33），claude 0.74（conflict recall 0.92）；plan 影响页面 recall 1.00。

结论：第 5 轮的规则过拟合了开发集，盲测下只能抓到三分之一的过时说法。第 6 轮只修了盲测集暴露出的通用 bug：注入检测把正常的接口文档行（例如 Bearer 请求头）误判为外发；数量规则只认紧挨着的数字，也不区分 200KB 这类带单位的值；不存在的项目式类型名（如 …PageBuilder）被放过；构建配置（compileSdk）没有纳入核对。平台范围类、功能不存在类断言属于语义判断，交给 claude 模式。修复后在 5 个真实仓库上复跑，冲突误报都是 0。每条规则都需要盲测集来约束。

6.4 真实 agent 使用 skills · 6.5 claude 模式

demo/skills-demo.sh：haiku 问“购物车上限三端分别是多少”时触发 kb-query，调用 kb parity，5 轮、$0.008 答出 50 / 99 / 50；问“wiki 是否与代码一致”时触发 kb-lint，17 轮，全程只读。claude 模式下每次 compound 最多分配 2 个 LLM 任务，所有步骤 verify 通过，写集以外的写入会被自动回滚。

6.6 不依赖 GitHub：每次 push 到 master 触发 compound（demo/hook-demo.sh）

先在本地建一个 bare 仓库作为“服务器”，用 kb hook install --mode post-receive 安装钩子。然后连续 push 三个 merge：先 push 01，0.8 s 后 push 02，再过 0.3 s push 03。demo 里用 kb-slow 模拟每次 3 s 的 LLM 耗时，让几次 push 在时间上重叠。

实测（remote: 输出）：seed 全量 9 个任务；01 增量；02 拿到锁时 master 已经是 03，因此一次追平（e6cff74..1c373e4 (4 new commit(s))）；03 输出 already compounded。每次都 verify PASS。

最终 remote master 与 wiki 的 last_sha 一致。实现要点：用 mkdir 锁保证串行；拿到锁后读取分支的当前头，从 last_sha 开始增量；wiki 放在服务端目录（--wiki-dir），不回写 master，因此不会递归触发钩子。

6.7 Agent A/B 基准：有 wiki 与没有 wiki（bench/agent-qa/）

同一组可以用正则核对的问题，用 claude -p --model haiku 分两组跑：A 组是仓库 + wiki + kb skills，B 组是同一份源码，只能用 grep 和读文件。minishop 上 10 题 × 3 次，A 和 B 都是 30/30，A 平均 9.0 turns、$0.25，B 平均 12.7 turns、$0.29。

“三端不一致”这题 A 用 11 turns，B 用 39 turns；“过时文档”这题有了 kb conflicts 后降到 4.7 turns。Cases 上的查找题两组持平。

9局限与路线图

当前局限

  • 运行时：TypeScript 版用 web-tree-sitter 加载随包发布的 WASM 语法，不需要 C 编译器；冷扫描比旧 Go 版慢（见 README 性能表），热扫描靠内容 hash 缓存。修改语法源码后需重新编译 WASM 并更新 GrammarHash，有测试强制检查。
  • 引用解析：基于名称、作用域和 import，没有完整的类型推断，也不建立跨平台的边。
  • facts 启发式：规则抽取在没见过的写法上泛化很差（见 5.5），需要盲测和 LLM 兜底配合。
  • 多级目录 / SFK：template 模式的节点摘要和文档条目是确定性的“目录式”文字，叙述质量要靠 --llm claude / --agent；L1 项目探测依赖构建标记（Gradle / SwiftPM / Xcode / hvigor），自研构建系统只能按平台启发式；SFK 的 adopted 文件只追加，不会改写人写的过时句子（只在 kb docs stale-specs / kb conflicts 中报告）。
  • 断言核对：template 在盲测集上的 conflict recall 只有 0.33，修复后为 0.58，所以它只能作为初筛。平台范围、功能是否存在这类语义判断需要 claude 模式（盲测 recall 0.92），单个任务约 30–60 s。

路线图：SCIP / LSP 精确引用；与 e2epilot 双向打通；用真实模型评测 Codex / Gemini；更小、可延迟加载的扫描缓存。
