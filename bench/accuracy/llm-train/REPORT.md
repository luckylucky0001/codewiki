# `kb compound --llm-facts` 在 16 仓训练集上的评估

- kb：`ts-rewrite` @ `e5288b1`，haiku（`claude -p`），先 16 仓 × 10 个候选文件，再对 6 个有漏检的仓库扩到 25 个候选文件（缓存复用）；总成本 **$0.448**。
- 基线：同一次运行的 facts 去掉 `source:"llm"` 条目，复现了纯规则的训练集数字。

## 召回与误报（micro）

| 指标 | 纯规则 | + LLM | Δ |
|---|---|---|---|
| routes recall | 98.6% | 98.6% | 0 |
| not_screen FP | 7.0% (6/86) | 8.1% (7/86) | +1 |
| deeplinks recall | 92.4% | 92.4% | 0 |
| testids recall | 95.8% | 95.8% | 0 |
| apis recall | 96.2% | 96.2% | 0 |

规则在训练集上已经到了 96–99%，剩下的漏检有两类：一是所在文件不在 LLM 候选范围内（候选只选规则几乎没有产出的文件），二是 LLM 本来就不处理的类型（Objective-C 深链、testID、静态资源）。

## LLM 实际写入的条目（标签外增量）

最终写入 facts 的 LLM 条目共 34 条（17 route + 17 API），分布在 8 个仓库。全部 34 条都做了人工审计：

| 类型 | 总数 | 正确 | 重复 | 部分正确 | 错误 | 严格精度 |
|---|---|---|---|---|---|---|
| route | 17 | 11 | 4 | 1 | 1 | 64.7% |
| api | 17 | 17 | 0 | 0 | 0 | **100%** |

- API 全部是标签里没有的真实端点，HTTP 方法逐条核对过，例如 NetNewsWire ReaderAPI、AntennaPod Nextcloud、mastodon endorse。
- route 的问题：
  - 4 条是规则已有页面换了一种 id 写法，去重没合并上；
  - 1 条是系统播放器 `AVPlayerViewController` 被当成页面；
  - 1 条是空占位页面。
- 16 仓全部 `kb verify` PASS。

## 结论与后续

- 在训练集上，`--llm-facts` 对打分指标没有收益，API 增量的质量很高。它的价值体现在没见过的写法上：heldout3 盲测中 routes 从 48.4% 提到 89.1%，APIs 从 19.7% 提到 39.4%。所以它保持默认关闭，作为面向新仓库的兜底手段。
- 针对 route 的这些问题，已加入三条通用规则：按目标 symbol 或文件去重；证据只是字符串数组元素时拒绝；拒绝系统框架类（`AV*`/`UI*`/`NS*`/`SF*` 等）。
- 还没做：候选选择应纳入"规则已有命中、但可能不完整的 API 服务文件"（会增加成本）。
